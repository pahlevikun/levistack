# Source audit and implementation boundaries

## Map the path before judging its shape

Read project instructions, current Git state, manifests, entry points and existing architecture/design documents. Trace the affected task from UI/API/command through policy, persistence and external effects. Inspect imports and real callers before naming an architecture. A directory named `domain` does not prove dependency direction.

If an indexed code graph is available, confirm project, generation and coverage; fill gaps with direct source reads. Otherwise use source search and disclose the discovery limit. Read complete affected units and their tests, then expand to their callers and shared state. Do not claim exhaustive coverage from a partial graph or a few matching files.

Produce a compact map of entry point, policy/state owner, effect boundary, data contract and evidence paths. Separate current behavior from plans and examples in older documents. Confirm supported platforms, storage, authentication and permissions from current configuration.

## Prioritize concrete findings

For each finding record severity, observed behavior, user/developer impact, source location, reproduction/evidence and the condition that closes it. Mark suspected risks as inferred until reproduced. Prioritize blocked tasks, data loss, privacy boundaries, invalid/stale state and inaccessible paths before visual drift or cleanup. Audit-only requests produce findings and a plan; they do not authorize repairs.

Inspect these seams when the changed task uses them:

- External data is parsed and validated before mutation. Validate complete import documents before writes; preserve complete stored records rather than casting a read projection into a writable entity.
- One owner performs each fresh-read/modify/write operation. Queue failure must not poison later work; avoid nested enqueue deadlocks. Name whether serialization covers a task, process, profile or shared store.
- Side effects use the identifiers returned by the operation. A before/after collection difference can include unrelated concurrent work.
- Persisted/private/ephemeral records keep their origin flags until the storage decision. Rendered or imported data alone does not establish trustworthy provenance.
- Cancellation, removal and timeout have explicit lifetimes. Returning a bounded output is different from bounding generated bytes, temporary files or child processes.

## Keep code understandable

Apply SOLID, DRY, KISS and YAGNI through observed responsibilities and change cost. Prefer the smallest structure that preserves rules. Reuse a real shared primitive before creating another abstraction. Remove unreachable code, redundant wrappers, duplicate state and stale compatibility paths within scope. Preserve deliberate differences in domain meaning.

Keep policy distinct from framework and I/O decisions where the existing structure supports that boundary. Do not invent ports, repositories, event buses or new deployables to decorate a small fix. Introduce a seam when actual volatility, multiple callers or a test boundary justifies it. Describe an architecture change by its trade-off and acceptance check.

Keep names tied to user/domain intent. Derive state when possible and restrict mutation to its smallest owner. Comments explain non-obvious external constraints or public contracts; remove narration, obsolete alternatives and blanket suppressions. Preserve licenses and useful explanations. Tests assert externally observable behavior rather than duplicating implementation branches.

## Model asynchronous interaction identity

An entity ID answers which record; it does not identify a visit, editor or command. Choose the identities the real flow needs:

| Identity | Invalidated by | Prevents |
|---|---|---|
| Selected entity | Selecting another record | Editing old detail under a new selection |
| Navigation/selection generation | Leaving and revisiting, including A → B → A | Old completion taking over a later visit |
| Editor session | Start, Cancel, close or replacement editor | Old Save closing/refocusing a newly opened editor for the same record |
| Submitted draft revision | Editing after submission in the same session | Old Save replacing or closing a newer unsaved draft |
| Request/run ticket | New request/run or completion | Old result clearing a newer pending operation |
| Registration lifetime | Removal or replacement | Retired work updating a current presentation |

Capture identity before awaiting. Recheck it after asynchronous hops, before applying data, navigating, clearing pending state or scheduling focus. Deferred focus callbacks also recheck identity. Choose an explicit edit-while-saving policy: disable editing during submission, or capture the submitted revision and preserve any later draft when that response arrives. Session identity alone cannot distinguish two drafts in one open editor. Keep drafts on failure. Closing an editor does not undo a write already accepted by the service; describe cancellation honestly.

Exercise delayed success and failure, selection changes, A → B → A, Cancel → reopen the same record, submit revision 1 → edit revision 2, repeated submission and unmount/removal. For revision tests verify that editing is deliberately blocked or that either old response preserves revision 2. Check data, current editor, draft, pending state and focus. Use controllable deferred responses rather than timing guesses.

## Implement and review a bounded slice

Record affected files, owner, inputs, dependencies, invariants, acceptance and checks before writing. Reproduce a defect on the relevant surface before fixing it. Prefer a meaningful behavioral regression when the failure involves state, data or lifecycle; a reversible token/copy edit can use direct artifact inspection.

Delegate only when session authorization and tools permit. Assign disjoint files or isolated copies; give shared assets one owner. The parent supplies source evidence and integrates results. Review specification compliance and maintainability/behavior separately. Fix material findings, rerun affected checks and re-review closure. Passing tests do not replace an independent reviewer when one is required; unavailable review is reported as unavailable.

Change technology only for an authorized need with current evidence. Compare staying with the incumbent against plausible alternatives using compatibility, migration/data risk, team operations, performance needs and maintenance cost. A tool preference is not a migration requirement. Derive commands from the actual project, preserve unrelated work and keep Git/release actions within current authorization.

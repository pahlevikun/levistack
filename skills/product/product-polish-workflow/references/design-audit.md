# Design audit and direction

Use this procedure when the request asks whether an existing design works or whether to refine or redesign it. Scope a user-facing surface, primary user and task, constraints and available evidence first. Inspect the running product when feasible; read its implementation and content so a screenshot is not mistaken for behavior. If there is no real design yet, label the work a new design and proceed to a grounded plan.

## Gather evidence before judging

For each representative screen or state, record the task path, control labels and behavior, navigation, empty/loading/error/success/disabled/focus states, keyboard and assistive access where observable, computed type/spacing/color, contrast, content honesty and rendered motion. Measure bundle/network/runtime cost only when it is relevant and feasible; an estimate must say how it was made. Cite a file and line, screenshot region, recorded action or measured value for each material finding. Mark source-only conclusions as inferred. Do not manufacture a score for unobserved surfaces.

Use Dieter Rams' ten questions as lenses: does the design advance a real use; help the task; have a coherent aesthetic; explain itself; stay out of the way; represent its behavior honestly; age well; handle details and states; conserve attention and resources; and keep only what earns its place? Record concrete evidence for the applicable questions. Novelty and visual fashion never override usefulness, comprehension or honesty. A numeric score is optional; if requested, define the scale first, show evidence per score and do not turn a total into an automatic redesign verdict.

## Decide the smallest sound outcome

- **Refine** when the task path and information structure work, and specific interaction, copy, state or visual defects have local owners.
- **Redesign the affected flow or surface** when the primary task is blocked by its structure or mental model. Preserve useful data, brand and navigation contracts; identify migration and regression checks.
- **Design new** when no implemented interface or meaningful decision exists yet.

Name the evidence that would change the decision. Give three to five prioritized moves with owner, affected state and closure check. For audit-only requests, deliver findings and a concrete plan; do not edit product behavior. For authorized polish, implement the bounded fixes and verify them on the real surface.

For websites and new pages, inventory real copy, images, claims and the action the page serves before choosing composition. Make a specific visual direction with one memorable product truth; avoid borrowed page templates, fake proof and ornamental sections. In working app screens, preserve useful density and existing design-system constraints. Treat tokenized color/type, visible focus, narrow layouts, no-script visibility and reduced motion as checks where the platform supports them. Do not impose website hero, word-count, CSS-stamp or a particular lint tool on an existing app.
